✈️ 全球航空市场进入策略分析

BACKGROUND

项目背景

航空创业面临高度复杂的市场环境：航线资源、区域需求、客户价值、运营成本相互影响，仅依靠经验判断难以形成可靠决策。

核心目标：本项目从商业问题出发，搭建数据分析框架，探索 SkyBridge Aviation 的市场进入路径。
THOUGHTS

我的思考

数据分析的价值不只是发现规律，而是帮助回答：

进入哪里？服务谁？如何竞争？

因此没有停留在单指标分析，而是围绕市场规模、客户价值、区域机会和运营策略建立完整分析链路。

PROCESS

核心过程

  • 01 基于 MySQL 完成航空业务数据建模与查询分析
  • 02 分析全球客户分布、收入贡献与市场集中度
  • 03 通过客户价值分层识别不同消费群体
  • 04 构建价格体系与市场进入策略
  • 05 将数据结果转化为商业决策建议
RESULTS

项目成果

  • ✓ 完成 12 阶段数据驱动分析框架
  • ✓ 输出 14 章节战略报告
  • ✓ 从市场结构、客户价值、区域选择等维度提出创业方案

核心图表与产品结论

01 · 全球机场与战略优先级

市场进入决策起点

美国 P1 但 Cabotage 严管 → 首年不碰，列入 3–5 年目标；首年聚焦东南亚–南亚走廊（新加坡 4h 内 6 亿人口、航权自由化）。

非洲 / 太平洋岛国为 P4 长尾，适合第六航权枢纽延伸。CASE WHEN 把机场数量译成 P1–P4 优先级——SQL 服务商业决策最直接的体现。

02 · 收入 vs 基础设施错配

蓝海在「机场多、收入低」

北美收入高但航权壁垒锁死 → codeshare 导流至新加坡枢纽，而非直接经营。

基础设施过剩、收入贡献低的国家 = 二线机场低成本点对点机会；加拿大–亚洲密度低 + 寡头市场 → 战略性抢稀缺洲际资源。这种错配必须靠 SQL 跨表 join + 比例计算才能挖出。

03 · 航线行动矩阵

12 阶段综合 · 决策终态

前 11 阶段 SQL 汇总为一张执行图：每个行动码对应一句管理话术——守护核心时刻、OPTIMIZE 测试 5–10% 提价、REVIEW 90 天退出窗口。

数据分析的终极交付物不是「洞察」，是决策——把数据库直接翻译成可执行计划。

技术方案摘要

01

12 阶段渐进式框架，而非巨型 SQL

暴力做法

200 行巨型 join → 难 debug、易超时、50 维报表没人知道「该怎么办」。

12 阶段

每阶段一个商业问题；描述→诊断→预测→处方；临时表串联成可解释决策链。

判断：框架是把复杂问题拆成 PM 和业务方能跟上的颗粒度——讲不清楚，技术再强也没用。

02

技术方案摘要

01

数据采集：Selenium 而非 Requests

房天下页面大量 JS 动态渲染，且有反爬（频率、UA）。Requests 拿不到动态内容且易被识别；付费接口预算为 0。

方案 优点 缺点 采用
Requests 快、省资源 无动态内容、易封 否
Selenium 真实浏览器、抗检测 慢、耗资源 是
付费接口 稳定 单次 ¥3000+ 否

落地：随机 UA（9 种）+ 随机延迟（1–5s）+ 失败重试（5 次）+ 疑难页二轮处理。 结果：14 区共 57,730 条，成功率 99%+，平均每区约 25 分钟。

02

模型选型：Random Forest 而非 XGBoost

模型 CV R² CV MAE R² 标准差
Random Forest 0.7506 109.63 0.0306
XGBoost 0.7474 117.40 0.0298

硬指标几乎打平（精度差 0.32%）。纯技术可互换；PM 视角 RF 胜出：

  • • 可解释性：特征重要性可直接写进产品文案（如「面积决定 76% 价格」），XGBoost 需额外接 SHAP。
  • • 下游成本：B 端会问「为什么这么估」——RF 回答路径更短。

判断：选型看「哪个最容易被产品和客户消化」，不是只看 R²。

03

数据清洗：保留长尾豪宅

学术思路

3σ / IQR 砍掉离群值——R² 立刻好看，但假装豪宅市场不存在。

产品思路

保留合理极端值；高端段失灵反而是分段建模 / 人工兜底的产品信号。

做法：只过滤逻辑错误（总价/单价/面积 ≤0）+ 户型样本 <5 的稀有类型。保留率 62.7%。 判断：清洗目标是反映真实市场，不是让模型好看。

04

评估方式：5×5 重复 K 折

简单 train/test 的 R² 会随随机种子波动，单点数字不可靠。

  • • RepeatedKFold：5 折 × 5 次 = 25 次评估，得到均值 ± 标准差。
  • • 稳定性：标准差 0.0275，上线后不易「突然崩盘」。

对外汇报「R²=0.77」时，需附带「标准差 < 0.03」——单点 R² 是不负责任的。

技术方案摘要

01

双阶段匹配，而非一步到位

1.2M 销量 × 87K 车型笛卡尔积 ≈ 10¹¹ 次比较，直接打分不可行。

暴力做法

1.2M×87K 全量打分 → 数天级；同一车型重复计算。

双阶段

Step1：87K↔价格库建映射（~10⁷）→ Step2：销量查表 join。总量降 4 个数量级，笔记本约 1h 跑完。

判断：避免重复工作比堆 CPU 更重要——架构设计胜过十倍算力。

02

八维度评分：无标准答案的解法

学术思路

纯字符串相似度——「奥迪 A6L」与「奥迪 Q5」可能高分，但语义不同。

多维度评分

8 维独立打分；品牌 4 / 车系 3 / 年排 2 …；排量 ±0.3L 容差；≥8 高 / 5–7 中 / <5 低。

  • • 可解释、可调权、可分层——权重反映业务直觉，不只看代码复杂度
03

多线程 + 向量化

单线程 for + pandas apply 对 87K / 1.2M 要数天。

  • • Step1：ThreadPoolExecutor(8) + Lock + as_completed 进度跟踪 → ~20 分钟
  • • Step2：swifter 行级并行 + NumPy 向量化 + 按品牌预筛选 → ~40 分钟

判断：慢在解释器层；热点交给 NumPy/多线程，Python 能扛百万级。

04

维度失效法处理缺失值

删除 / 填充

删行丢 30%+ 长尾；填充众数会「骗高分」。

维度失效

缺失维不参与也不扣分；按可比较维度计分 → 信息不全自然落入中低置信。

判断：缺失是常态；反映真实可信度，不用假数据制造完整感。

05

输出 5 条战略建议，而非只交 CSV

常规交付

CSV + 描述统计——客户不知从哪看起，数据≠业务交付物。

走到决策

5 条结构化建议（基建 / 10–15万 EV / PHEV / TCO / 分城），每条附数据+政策+落地路径。

判断：客户买的是「接下来怎么办」——从信息到决策，是 PM 与纯分析师的分水岭。

BACKGROUND

产品背景

日常饮食选择存在高频、低价值但持续消耗精力的问题。用户往往面临：

不知道吃什么
想吃什么缺少灵感
决策反复消耗时间

本产品通过轻量化交互，将用户需求转化为个性化推荐结果，帮助用户快速完成饮食决策。

FEATURE

产品功能

个性化推荐 结合用户偏好信息，减少无效选择，提高推荐匹配度。
场景化决策 针对不同使用场景提供差异化推荐： 日常用餐 快速选择 随机探索
快速产品验证 通过低成本开发方式快速完成方案设计、页面交互、核心功能与体验验证，跑通从需求提出到产品落地的完整流程。
PRACTICE

产品实践

围绕「降低饮食决策成本」完成一次独立 C 端产品实践，从用户问题、核心路径到 MVP 验证形成完整闭环。

  • ·问题定义：从“缺少美食信息”进一步定位为选择过多 + 多重约束下的决策疲劳，将产品目标从“提供更多推荐”转向“帮助用户更快做决定”。
  • ·体验取舍：针对不同决策状态设计两条路径：有明确需求时提供 Top 6 个性化推荐；不想思考时直接一键决策，减少无效浏览与重复操作。
  • ·推荐机制：区分用户约束强弱：过敏 / 排斥做硬过滤，健康 / 心情做软排序，并设置结果不足时的降级兜底，平衡推荐相关性与结果可用性。
  • ·MVP 验证：聚焦偏好、推荐、决策三个核心环节，暂缓社区等非核心功能；以推荐接受率、重选率、决策时长、决策完成率作为后续验证指标。

📄 PRD · 今天吃什么

POSITION

一句话定位

「今天吃什么」是一款帮助用户降低日常饮食决策成本的轻量化 C 端决策产品。

通过偏好理解、有限推荐与一键决策，在保证结果可接受的前提下，减少用户搜索、比较和反复纠结。

PROBLEM

核心问题

用户缺少的并不是更多关于「吃什么」的信息。

菜谱平台、外卖平台、点评平台已经提供了大量内容，但当用户真正面对一顿饭时，仍然需要在：

口味 × 健康 × 忌口 × 心情 × 场景

等多个条件之间不断搜索、比较和排除。

因此本产品解决的并非

帮用户发现更多食物。

而是

帮助用户用更低的认知成本，完成一次“足够满意、可以立即行动”的饮食决策。

01

项目背景

1.1 问题来源

日常生活中，我持续观察到一种高频但容易被忽略的决策消耗：

  • ·家庭做饭前反复讨论“今晚吃什么”
  • ·上班族午休时间不断切换外卖平台，最后仍选择熟悉的食物
  • ·有健康、减脂或忌口需求的人，需要在大量菜品中逐个排除
  • ·用户面对大量推荐时，反而更容易陷入持续比较

这些行为共同指向同一个问题：

信息丰富并不意味着决策容易。

用户真正承受的是：

选择过多 多重约束 重复比较

带来的决策疲劳。

02

用户研究

2.1 研究目标

本次轻量研究主要验证三个问题：

  • 1用户在「今天吃什么」过程中真正困难的环节是什么？
  • 2用户需要更多选择，还是需要更少、更合适的选择？
  • 3什么情况下用户愿意直接把决策交给系统？
2.2 研究方式

受个人项目资源限制，本阶段采用轻量级定性研究：

  • ·二手研究：阅读菜谱、外卖及美食产品相关用户评价约 50 条
  • ·生活观察：观察家人、朋友、室友的实际饮食决策行为
  • ·用户访谈：与 5 位不同生活状态用户进行 15–30 分钟非正式访谈
研究边界

当前结论用于支持 MVP 假设形成，而非代表大样本用户结论。

如果进入真实商业验证阶段，应进一步通过：定性访谈 → 定量问卷 → 行为数据 持续验证。

03

核心用户洞察

3.1 洞察一：用户缺的不是选择，而是结束选择

常见产品逻辑是：给用户更多菜品。但在饮食决策场景中，更多候选往往意味着更多比较。

应从
增加供给
转向
缩短决策
设计原则：少而有效 > 多而丰富
3.2 洞察二：用户条件存在不同优先级

用户输入的条件并不具有相同权重。例如“花生过敏”与“今天比较想吃辣”不能使用相同的筛选方式。

硬约束
不可违反 · 花生过敏
软偏好
可以权衡 · 今天比较想吃辣

因此推荐系统需要区分：什么绝对不能出现，什么只是更希望出现。

3.3 洞察三：不同用户并不总想“挑”

用户存在两种明显不同的决策意愿：

状态 A

我愿意选，但不要让我选太多

有限候选推荐
状态 B

我已经不想思考了

系统直接替我决定

因此产品不能只提供一条推荐路径。

3.4 洞察四：推荐的价值不在于绝对精准

在低风险、高频的饮食决策场景中，用户并不需要理论上的“最优解”。

相比绝对准确，更重要的是：结果安全、符合基本偏好，并且让我愿意马上做决定。

MVP 优先追求：可接受性 > 绝对精准度
04

目标用户

本产品不以职业、年龄作为主要用户划分，而根据用户进入产品时的决策状态进行设计。

用户状态 典型表达 核心需求 产品任务
无明确想法“完全不知道吃什么”缩小范围提供有限候选
有模糊偏好“今天想吃清淡一点”找到符合状态的结果个性化推荐
有明确限制“不能吃花生 / 今天不吃辣”避免不可接受结果条件过滤
不想继续思考“随便，帮我选一个”直接结束决策一键决策
05

Jobs To Be Done

用户真正雇佣这个产品完成的不是

“帮我浏览美食。”

而是

当我需要决定一顿饭、但不想投入太多时间思考时，帮我快速得到一个符合基本需求、可以直接接受的选择。

核心 Job

  • ·Functional Job：快速决定吃什么。
  • ·Emotional Job：减少纠结和反复比较带来的心理消耗。
  • ·Supporting Job：在存在健康、忌口等限制时，避免明显不适合的选择。
06

产品定位

6.1 定位

轻量化饮食决策工具

不是：

菜谱大全 外卖平台 餐厅点评平台 健康管理 App
而是：帮助用户完成“吃什么”决策的最后一公里。
6.2 核心价值主张
更少输入

长期偏好建立后持续复用。

更少选择

不通过无限内容流增加决策成本。

更快决定

既可以自己从有限结果中挑，也可以直接让系统替用户选择。

07

产品目标

7.1 用户目标

帮助用户：更快完成一次满意的饮食决策。

7.2 MVP 产品目标

首版重点验证三个核心假设。

H1｜偏好复用假设

用户愿意在首次使用时提供少量偏好，以换取后续更低的操作成本。

H2｜有限推荐假设

有限、高相关性的候选结果，比大量内容更容易帮助用户完成选择。

H3｜决策代理假设

在部分场景下，用户愿意让产品直接替自己完成选择。

7.3 非目标

MVP 阶段暂不追求：

内容丰富度最大化 社区活跃度 用户停留时长 完整饮食健康管理 复杂 AI 能力展示
产品成功标准不是

用户在这里待了多久。

而是

用户多快离开产品去吃饭。

08

产品设计原则

8.1 低决策成本 > 信息丰富度

任何新增信息都需要回答：它是否真的帮助用户更快决定？

8.2 约束优先 > 兴趣偏好

安全、过敏、明确排斥等条件必须优先于推荐准确度。

8.3 可接受 > 理论最优

低风险高频决策中，一个“足够不错”的答案比长时间寻找“最好答案”更有价值。

8.4 用完即走 > 用户停留

不通过以下方式人为延长用户使用时长：

无限下拉 排行榜 红点提醒 高频消息推送
8.5 AI 在后台 > AI 在前台

用户不需要感知模型本身。AI / 算法只有在能够减少操作成本 / 提高推荐质量 / 提升效率时才有使用价值。

11

功能需求

F1｜用户偏好
P0

通过少量结构化信息建立用户基础画像，为后续推荐提供条件。

长期偏好

可持续复用

口味偏好饮食习惯健康倾向过敏信息长期忌口
即时状态

主要影响当前决策

当前心情今天想吃今天不想吃当前场景

设计原则：避免一次要求用户填写过多信息。首轮只获取足够影响推荐结果的信息，其他偏好可在后续使用过程中逐步补充。

F2｜个性化推荐
P0

从候选池中输出符合当前用户状态的有限结果。默认返回 Top 6，而不是无限列表。

产品解决的本身就是选择过多，因此推荐系统不应该重新制造一个新的信息流。Top 6 需要同时保证：一定选择空间、一定推荐多样性、不产生明显比较压力。

推荐卡片信息

菜品名称 核心标签 简短推荐理由 是否符合当前关键偏好

避免出现大量非决策必要信息。

F3｜帮我决定吧
P0

服务已经没有继续比较意愿的用户。系统从当前可接受候选池中直接返回一个结果。用户只需要判断「可以 / 不可以」，而不是继续判断「哪个最好？」

首次结果：今天就吃这个 → 用户操作：就它了 / 再来一个。

将复杂的

多选一问题

降维成

是 / 否问题

进一步减少决策成本。

F4｜偏好调整
P0

用户可从结果页快速调整：当前想吃、当前不想吃、忌口、偏好。修改后立即重新计算推荐。

12

推荐策略

硬过滤 → 软排序 → 降级兜底
12.1 第一层：硬过滤

满足以下条件的候选直接移除。

  • ·过敏：例如花生过敏。涉及安全风险，不允许参与排序。
  • ·明确忌口：例如不吃香菜。
  • ·当次明确排斥：例如今天不想吃辣。
硬约束的意义不是

降低推荐分。

而是

不应该出现在候选池。

12.2 第二层：软排序

通过硬过滤后的候选进入评分阶段。影响因素包括：健康偏好、口味、当前心情、当前场景、用户长期偏好。

推荐得分 = 健康匹配 × 3 + 当前状态匹配 × 2 + 基础偏好匹配

最终按得分排序输出。

为什么 MVP 使用规则推荐

当前阶段用户数量有限、行为数据不足、条件较结构化，且推荐需要较强可解释性。因此相比直接使用复杂 ML / LLM，规则策略更适合 MVP 验证。

可解释 可控 成本低 易排查 易调整
此阶段首先验证

产品逻辑是否成立

而不是

模型是否足够复杂。

12.3 第三层：降级兜底

如果用户同时设置：低脂 + 不吃辣 + 素食 + 不吃豆制品 + 当前想吃暖胃，可能导致候选数量不足。系统不能简单返回「暂无推荐」。

  • ·Level 1：保留所有硬性条件，降低部分软偏好权重。
  • ·Level 2：继续保留安全及明确忌口条件，放宽心情、非核心健康偏好。
  • ·Level 3：返回基础可接受候选，并说明：“符合全部条件的选择比较少，先为你保留最重要的饮食限制。”
核心原则：推荐可以不完美，但不能不可用。
13

场景处理方式
无偏好数据使用基础推荐池

功能取舍标准

每个新增能力都必须回答：它是否能够直接降低用户完成一次饮食决策的成本？如果不能，则不属于当前 MVP 核心范围。

15

数据指标

15.1 北极星指标

有效决策完成率

定义：进入推荐流程后，最终接受某个推荐结果完成决策的用户比例。

完成决策用户数 ／ 进入决策流程用户数

为什么不是 DAU？本产品不是内容消费型产品。使用频率和使用时长都不应该成为核心价值判断标准。真正应该验证的是：用户来了以后，有没有更快解决“今天吃什么”。

16

行为埋点设计

MVP 如果进入真实用户验证阶段，建议记录以下关键行为：

Event说明
decision_start开始一次饮食决策
preference_submit提交偏好
recommendation_view查看推荐
recommendation_accept接受推荐
recommendation_retry请求重新推荐
preference_change修改偏好
decision_complete完成决策

后续可以通过行为数据判断：用户说自己喜欢什么，和用户实际选择什么之间是否存在差异。

17

后续推荐迭代方向

V1.1｜建立反馈闭环

记录接受、重选、排斥、偏好修改，逐步修正用户偏好。

V1.2｜提升推荐多样性

解决连续推荐内容过于相似的问题。例如近期连续出现：番茄炒蛋 → 番茄牛肉 → 番茄意面。即使单项得分较高，也可能造成用户感知上的重复。因此增加新鲜度 / 去重因子。

V1.3｜行为学习

当行为数据积累后，将用户填写的显性偏好与用户实际选择的隐性偏好结合。例如用户填写不在意辣度，但过去十次选择中八次选择辣味菜品，系统可以逐步提高对应偏好权重。
